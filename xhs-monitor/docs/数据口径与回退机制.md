# 数据口径与回退机制

这份文档记录「已售数字为什么会掉下去」「我们怎么判」「代码在哪」。
调研与落地时间：2026-10-20 ~ 2026-10-21。

**为什么单独写一份**：这件事上我们错过一次（把"延迟数据"当成了"剔除退款"），
而且错得很有说服力——数字确实掉了，掉完确实又涨回来了，只是涨回来的方式
暴露了真相。下次再遇到类似现象，先看这份文档的「证据链」部分，
别急着下结论。

---

## 0. 一分钟速查

| 问题 | 结论 |
|---|---|
| 数字掉下去了，怎么办？ | 分两种：涨得回来的 = 延迟数据，剔除；涨不回来的 = 真回调，如实显示负数 |
| 什么时候采集？ | 只在 **07:30–23:50**，凌晨不采 |
| 今日增量怎么算？ | 最新可信值 − 基线，基线 = **「昨日最后」与「今早首采」取低者** |
| 今日增量和图表数字对不上？ | 正常。**今日增量 = 图上今天的值 + todayCut** |
| 店铺 / 分组的销量怎么算？ | **各品先算本周期增量，再相加**。绝不能先把累计值求和再跨期相减（新增商品会灌进它全部历史） |
| 想改采集时间 / 看日志 | 右上角「采集管理」→ 自动采集段；窗口外的时间点会标红且不会执行 |

## 1. 现象：凌晨的「已售」会掉下去

### 1.1 原始证据（2026-10-21，本地时间，来源 `data/snapshots.json`）

```
电容笔 pmvgmzka6
  10/20 23:40 = 1857  → 10/21 00:15 = 1860 → 00:30 = 1861 → 08:18 = 1868 → 10:04 = 1872
  （这条当天没掉，是前一版事故里的样本，见 1.3）

猫猫 pmvgpc6x5
  10/20 23:40 = 1661  → 10/21 00:15 = 1647 ↓  → 00:30 = 1662 ↑  → 08:18 = 1665 → 10:04 = 1667

森之物 pmvgrzoov
  10/20 23:40 =  556  → 10/21 00:15 =  550 ↓  → 00:30 = 550 → 08:18 =  557 ↑  → 10:04 = 557

眼罩 pmvgqwp4z
  全程 54000 不变（原文「已售5.4万+」，见第 2 节）
```

两条掉下去、之后又涨回来，**还涨过了掉之前的高点**（1662 > 1661，557 > 556）。

### 1.2 第一版结论：错的

> 「0 点数字下降 = 平台在日切时剔除退款/取消单」

这个结论看着很合理，也符合业务常识。当时的实现是：给 0 点那条特殊待遇，
把它当今日基线，这样日切修正就不会算进当天销量。

**它错在哪**：如果真是剔除退款，数字掉下去之后**不可能自己涨回来**。
退款只会让累计件数减少，不会还回来。而实测里它涨回来了，还超过了掉之前的高点。

更细的反证：电容笔那次 15 分钟涨了 82 件（1778 → 1860），发生在午夜。
这个速率在凌晨不合常理。

### 1.3 正确结论：凌晨读到的是旧快照

**掉下去 → 之后涨回并超过掉之前的高点 ⇒ 那条低读数是延迟数据，不是真实销量。**

判定只需要一个事实：**之后有没有涨回到那个高点**。不需要设阈值
（设阈值就又回到"猜"了，而且我们在这上面已经错过一次）。

补充证据：正常时段用探针连打 8 次（间隔 9 秒），读数完全一致 —— 不抖。
问题只出现在日切窗口。

## 2. 另一个独立问题：高销量商品是取整显示

`priceH5.itemAnalysisDataText` 的分辨率：

| 已售量级 | 原文 | 分辨率 |
|---|---|---|
| < 1 万 | `已售1868` | 精确，1 件 |
| ≥ 1 万 | `已售5.4万+` | **1000 件一档** |

所以「眼罩」那条平线不是没卖，是档位太粗看不出来。

- 采集侧：`api_collect.js` 的 `soldResolution(raw)` 解析出 `{approx, step}`
- 历史数据（没有这两个字段的老快照）：`store.js` 的 `coarseInfo(snap)` 从 `note` 反推
- 界面：累计值显示 `≈54,000*`，悬停说明"平台按 1,000 件一档"

**这类商品的今日增量可能是 0，不代表没卖。**

## 3. 规则总览：两道防线 + 一个基线

```
原始快照序列
    │
    ├─ 第一道：soldSeries()          ← 剔除「涨回来了」的延迟数据
    │
    ▼
可信序列（单调不减，除非真回调）
    │
    ├─ 第二道：TRUST_WINDOW          ← 源头不采，避免"没机会翻案"的脏数据
    │          （07:30–23:50）
    │
    ▼
今日基线 todayBaseline()             ← 「昨日最后」与「今早首采」取低者
    │
    ▼
今日增量 todayDelta()
```

### 3.1 第一道防线：过期读数剔除

**位置**：`store.js` → `soldSeries(db, productId)`

```
遍历按时间排序的成功快照，维护当前高点：
  当前值 < 高点 ？
    ├─ 之后有一条 ≥ 高点  →  剔除（延迟数据）
    └─ 之后再没回到高点   →  保留（真回调，如实显示负增量）
```

三条性质：

- **只用事后可知的事实**，不设阈值
- **最后一条如果是掉下来的，暂时判不了，先保留** —— 它本来就是最新事实
- 涨回去但**没超过**高点 → 保守保留（不敢断言）

被剔除的记录在历史弹窗里标「过期读数·已剔除」，**不算采集失败**。

### 3.2 第二道防线：可信时段

**位置**：`scheduler.js` → `TRUST_WINDOW = { start: '07:30', end: '23:50' }`

**为什么有了第一道还要第二道**：`soldSeries` 是事后补救，前提是后面得有一条
涨回来的记录。若凌晨那条恰好是当天最后一条（服务停了、下次采集失败），
它就**再也没机会翻案**，会被永久当成真实退款留在数据里。

与其事后救，不如源头别采。

**代价**：看不到 00:00–07:30 的分时走势。但这几个小时的销量不会丢，
整段归到当天（按日统计本来就该这样算）。

生效范围（三处，缺一不可）：

| 位置 | 行为 |
|---|---|
| `shouldRunNow()` | 窗口外的槽位一律不执行 |
| `nextRun()` | 过滤窗口外槽位，否则会显示一个永不执行的「下次执行」 |
| `server.js` 启动逻辑 | 「启动即采集」同样受限 —— 凌晨重启服务不会抢跑一次 |

界面侧：设置弹窗里窗口外的时间点**标红 + 文字警告**，避免"设了却不知道不执行"。

### 3.3 今日基线：取低者

**位置**：`store.js` → `todayBaseline(db, productId, refTs)`

```
候选 A = 昨日最后一次可信读数
候选 B = 今天第一次可信读数

基线 = min(A, B)
  - 通常 B > A（夜里一直在卖） → 用 A，夜间销量算今天
  - B < A → 用 B。那笔下修发生在昨天和今天之间，不该把今天的数字压成负数
```

#### 易错点 1：阈值拿「昨日最后」比，不是「昨日最大」

昨天盘中出过真退款时，两者不等：

```
昨天 12:00 = 1000
昨天 18:00 =  990   ← 真退款，之后再没回到 1000
昨天 23:49 =  990   ← 昨日最后
今早 07:31 =  995   ← 比昨夜高 5 件（货真价实的夜间销量），但比昨天最高点低 5 件
今天 12:00 =  998
```

- 拿「最后 990」比：995 > 990 → 基线 990 → 今日 **+8** ✅
- 拿「最大 1000」比：995 < 1000 → 误判"今早掉了" → 基线 995 → 今日 +3，白丢 5 件

**用例**：`test_rollback.js` 的 C 组专门钉住这点。

#### 易错点 2：这条规则只在「全天没涨回昨夜高点」时才会触发

```
昨夜 23:49 = 1000
今早 07:31 =  993   ← 更低
今天 12:00 = 1030   ← 但涨回来了，还超过了 1000
```

这种情况下 `soldSeries` **早就**把 993 当延迟数据剔除了，轮不到基线规则。
序列变成 `[1000, 1030]`，基线仍是 1000，今日 +30，吸收量为 0。

**两道防线各管一段**：`soldSeries` 先筛假回退，基线规则只处理剩下的真下修。

**用例**：`test_rollback.js` 的 B2 组钉住这点。万一哪天 `soldSeries` 被改坏
（比如把这条低读数留下了），那条用例会立刻变红。

### 3.4 不静默吞账：`todayCut`

今早首采更低时改用 B 当基线，会**吸收掉一笔下修**：

```
昨夜 1000 → 今早 993 → 中午 998
今日增量 = 998 − 993 = +5
但累计其实比昨夜低 2 件 —— 看着在涨，实际在跌
```

所以吸收量记在 `todayCut`，沿三条链路带到界面：

- `store.stats()` → `todayCut` / `todayBase`
- `store.groupByShop()` / `store.groupCompare()` → 同上
- `server.js` 的 `/api/state` → 同上

界面：数字后紧跟 `↧7`，鼠标悬停显示
「今早首采比昨夜低 7 件，已改用它作今日基线，这笔下修未计入今日增量」。

## 4. 与图表的关系（两者会差一个数，这是有意的）

| 口径 | 算法 | 上例结果 |
|---|---|---|
| 按日销量图 | 本期最后 − 上期最后 | 945 − 1000 = **−55** |
| 今日增量 | 最新 − min(昨日最后, 今早首采) | 945 − 940 = **+5** |

**恒等关系：今日增量 = 图上今天的值 + todayCut**（−55 + 60 = 5）。

图表现的是"累计口径的变化"，今日增量表现的是"今天的经营结果"。
两个都要，不要试图统一——统一就意味着有一边在说谎。

### 4.1 店铺 / 分组怎么加总（`ChartKit.sumDeltas`）

**先按每个商品算出本周期的增量，再把同一周期的增量相加。**

不能反过来（先把各品累计值求和，再跨周期相减）。两者在「每个品都有上一期基线」
时结果相同，一旦某品缺上一期就天差地别：

```
甲店  重力眼罩    昨天 21:55 已售 54000 → 今天 11:00 已售 54010   （今天卖 10 件）
甲店  亏本出同款   今天 11:27 才加入监控，首采 1635 → 11:47 的 1642  （今天卖 7 件）

逐品先算：10 + 7 = 17                        ✓
先加后减：累计 54000 → 55652，相减 = 1652     ✗ 把新商品一辈子的 1635 件算成今天卖的
```

这条不是理论推演——2026-10-21 真实发生过：用户在「君君会睡觉的店」新增了一个同类商品，
图上当天凭空多出 +1635，而那个商品一件都没多卖。

配套的两条规则：

- **新加入监控的商品只从它第一次采集起算**（首采即基线 → 空心圈 + `≈`），
  之前的历史销量不计入任何周期。所以「某品本期只有一条读数、又没有上期」时
  它这一期就不参与相加（不编 0，也不影响其它品）。
- **「区间合计」只累加店铺/汇总这一层的线**。选中多品店铺时图上同时有单品线和
  店铺汇总线，全加一遍会把每个品算两次（17 会变成 34）。

> **累计走势图是例外，别一起改**：它是各品「已售」的和。多监控一个商品，
> 这个和自然要抬一截——那不是销量。所以累计线在新增商品处会有一个台阶，
> 而增量线不会。两个图本来就表达两件事。

自检口径：**各品周期增量相加 = 店铺线；各店铺线相加 = 区间合计。**

## 5.1 24 小时加购数（`cartCount`）—— 与销量不是一个口径

**它是什么**：商品页展示的「近 24 小时 N 人加购」，是**即时快照**：
既不是累计量，也不是本周期的增量。

因此三条硬规则：

1. **只取最新一次读数**（`latestCart()`）。上周加购 800、今天 120，有效值是 120；
   拿老的读数做差没有意义。
2. **不参与任何差值计算**。今日增量只跟「已售」走，加购再高也不影响。
3. **没有就是 `null`，不是 0**。0 会被读成"一个加购都没有"。
   `sumCart()` 全为 null 时返回 null，不是 0。

**当前现实：拿不到。** 2026-10-21 实测 11 个在监控的商品，接口返回的
`priceH5.itemAnalysisDataText` 全是「已售X」——免登录接口不公开这个字段。
解析逻辑照样完整实现（先看销量文案位，再 `findCartDeep()` 全接口兜底扫描），
平台哪天放出来就有数，不用改代码。

### 易错点：别把加购文案当成销量

加购文案和销量文案**共用同一个展示位**。而「24小时内123人加购」里
第一个数字是 **24（小时数）**。不加闸的话 `parseSold()` 会解析出"已售 24"，
那是**凭空造出来的销量**，比"数据不准"严重得多。

所以 `parseSold()` 现在先判断：含加购、且不含「已售/销量/已购买/售出/人付款」
这类销量标志 → **直接返回 null**。

### 易错点：销量采集失败的那条快照，加购照样有效

`latestCart()` **刻意不过滤 `ok`**。某次采集可能销量没读到（判失败）但加购拿到了，
那条加购依然是当时的真实读数。

### 易错点：加购求和按品算，和销量一个道理

店铺 / 分组的 `totalCart` = 各商品**最新**加购数之和。
没有加购数据的品不计入（不补 0），否则会把"没采到"压成"没人加购"。

## 6. 操作手册

### 6.1 改采集时间

右上角「采集管理」→ 自动采集段。当前设置：

```
07:31   10:00   12:00   15:00   18:00   21:00   23:49
```

也可以直接改 `data/schedule.json`（服务每 20 秒重读一次，不用重启）：

```json
{
  "enabled": true,
  "times": ["07:31", "10:00", "12:00", "15:00", "18:00", "21:00", "23:49"],
  "runOnStart": true
}
```

> **末采 23:49 为什么重要**：它同时是明天的基线起点。原来末采是 21:00，
> 意味着**昨天 21:00–24:00 那 3 小时的销量被算进了今天**。挪到 23:49 后，
> 归属误差从 3 小时缩到 11 分钟。这个收益跟凌晨脏数据无关，是独立的口径修正。

### 6.2 重启服务

**必须带两个环境变量**，否则 `collect.js` 引不到 playwright，直接 MODULE_NOT_FOUND：

```bash
cd xhs-monitor
NODE_PATH=~/.workbuddy/binaries/node/workspace/node_modules \
PLAYWRIGHT_BROWSERS_PATH=~/.workbuddy/binaries/node/workspace/browsers \
PORT=7788 node server.js
```

跟 `启动监控.command` 里的写法保持一致。

启动后日志会打印可信时段和下次执行时间，用来确认配置生效：

```
  采集时间: 07:31、10:00、12:00、15:00、18:00、21:00、23:49
  可信时段: 07:30–23:50（窗口外不采集，凌晨会读到旧快照）
  下次执行: 2026/10/21 12:00:00
```

### 6.3 改配置 / 改逻辑后怎么验证

```bash
cd xhs-monitor
bash run_tests.sh          # 全部（约 2.5 分钟）
bash run_tests.sh core     # 只要不需要浏览器的那批（约 20 秒）
```

`run_tests.sh` 会先把 `data/snapshots.json`、`data/schedule.json` 备份到
`backups/<时间戳>/`，跑完比对 MD5，一旦被测试改动就打印还原命令。

**跑全量前先重启服务**。旧进程没有窗口守卫，可能按旧时间表在测试期间采集，
改动 `snapshots.json` → MD5 校验误报「被污染」。

### 6.4 核对当前数据

```bash
curl -s http://127.0.0.1:7788/api/state | python3 -c "
import json,sys
s = json.load(sys.stdin)
print('今日增量合计:', s['totals']['today'])
for p in s['products']:
    cut = f\"  ↧{p['todayCut']}\" if p.get('todayCut') else ''
    print(f\"{(p['name'] or '')[:20]:22} 累计 {p['cumulative']:>6}  今日 {p['todayDelta']:>4}{cut}  基点 {p.get('todayBase')}\")
"
```

跑测试必须通过 `run_tests.sh`，不要单独跑 —— 备份和数据校验在这一层。

> **`run_tests.sh` 会先探测 7788 上有没有服务。** 四个只读界面测试
> （`test_ui_lastnext` / `test_ui_overview` / `test_ui_today` / `test_ui_period`）
> 直接连真实服务，服务没起时会报 `ERR_CONNECTION_REFUSED`，
> 表现成「无法运行」，容易被误当成代码问题。脚本现在会区分这两种情况。

> **服务在跑的时候，数据 MD5 必然会变**（它自己会采）。所以脚本在 MD5 不同时会
> 再做一次结构比对：只允许「追加新快照 + lastRunAt 更新」，一旦有商品/快照丢失
> 或已有快照的已售值被改写，才判污染。别因为看到 ✓ 就以为服务没在写数据。

> **后台起服务要用受管任务，不能用 `nohup`。**
> `nohup node server.js &` 起的进程在 Bash 调用结束后会被沙箱回收，
> 表现为「刚启动还能访问，几分钟后 502」。
> 用 `run_in_background: true` 起，并在每次跑测试前确认 7788 还活着。

## 7.6 加购数：平台当前不公开（调研记录）

用户问「24h 加购这个数据一个都没有拿到吗？」。答案：**一个都没拿到，而且拿不到**。
下面是证据链，别再重复调研。

### 免登录接口：全量枚举，没有加购字段

`mall.xiaohongshu.com/api/store/jpd/edith/detail/h5/toc?version=0.0.5&item_id=<24位hex>`

- 一个商品返回 **220 个叶子**（字符串 + 数字），**215 个是中文**，全部打印看过
- 搜索「加购 / 想要 / 收藏 / 心愿 / 浏览 / 转化」：唯一命中是顶部菜单里的
  **「心愿单」**（一个功能入口的名字，不是数据）→ **误报**
- 数字类字段只有 `sellerH5.fansAmount`（粉丝数 2623）、`sellerH5.salesVolume`（已售 1.5万）
- 12 个商品逐个查 `priceH5.itemAnalysisDataText`：
  已售1919 / 已售1673 / 已售5.4万+ / 已售570 / 已售1635 / 已售6914 /
  已售2.9万+ / 已售1万+ / 已售9424 / 已售6266 / 已售1059 / 已售50
  → **全是「已售X」，无一例外**

### 浏览器渲染后的商品页：也没有

Playwright + iPhone UA 打开 `www.xiaohongshu.com/goods-detail/<id>`：

- 页面**能正常渲染**（innerText 559 字，含「已售1673」「到手价」「粉丝数 2623」等）
- 全文搜「加购 / 想要 / 心愿」→ **全部 false**
- 渲染后的 DOM innerHTML 里也没有
- 抓到的业务接口只有 `toc`（同一个接口）和 `webprofile`
  （另有 `redcaptcha/v2/getconfig`、`sbtsource`、`scripting` 等风控接口）

⚠️ 页面**第一次**用 `domcontentloaded` + 短等待时 innerText 长度是 **0** ——
那是风控挡了、还没渲染完，别误判成"页面没有数据"。
等 5~6 秒或用 `networkidle` 才拿得到文本。

### 候选接口：全部 404

`/h5/analysis`、`/h5/item_analysis`、`/h5/wish`、`edith/api/store/jpd/item/analysis`
→ 全部 **HTTP 404**。`toc` 加 `version=0.0.6&source=app` 也一样（仍是「已售X」）。

### 结论

**加购人数是平台不对外公开的数据**，不是我们漏采。
所以：
- 采集管道**保留**（`parseCart` 认文案 + `findCartDeep` 全接口兜底扫描）。
  `priceH5.itemAnalysisDataText` 是平台自己的「商品分析数据位」，
  它今天放已售、明天可能放加购 —— 平台哪天换过来，数就自动有了。
- 界面**必须说清是平台不公开**，不能让人以为工具坏了。
  原来写「暂时全是—」是含糊说法，已改成明确说明。
- 浏览器通道补了一条：接口成功但没带加购数时，用浏览器看一眼页面。
  **但必须有登录态**才做（没登录态时页面被风控挡，innerText 空，白跑）。
  当前 `auth/storage-state.json` **不存在**，这条暂时不触发；留好接口，登录态到位就生效。

### 顺带修的一个真 bug

`collect.js` 原逻辑：浏览器通道**只在接口失败时**才走。
所以「接口成功但没带加购数」时，页面上就算有加购也永远抓不到。
现已补上这条分支（见上）。

## 7.5 主数据区该放什么（一条版面原则）

主表格回答的是「谁在卖、卖了多少」。往里塞运维信息会稀释重点，
所以定了这条线：

| 类别 | 放主数据区？ | 放哪 | 例子 |
|---|---|---|---|
| 业务指标 | ✅ 放 | 主表格 | 累计已售、今日增量、24h加购、价格 |
| 口径修正记号 | ✅ 放，但要轻 | 主表格（小字 + 悬停） | `↧7`（todayCut）、`≈54,000*`（取整） |
| **当前状态**的数据健康度 | ⚠️ 只在成立时放 | 主表格（灰色小标 + 悬停） | 「数据旧」（最近一次采集失败） |
| **历史累计**的健康度 | ❌ 不放 | 采集管理 → 采集日志 | 「窗口内失败 N 次」 |
| 采集过程 | ❌ 不放 | 采集管理 | 立即采集、时间表、每轮日志 |
| 原始明细 | ❌ 不放 | 商品行「历史」按钮 | 每一次采集的读数 |

**为什么「失败N」要从主表格拿掉**（实测踩到）：
原实现显示「窗口内累计失败次数」。07:31 启用可信时段后**一次都没失败过**，
但那 3 条 00:00 旧制度下采的失败还挂在 7 天窗口里 → 表上一直显示「失败1」，
看着像现在还在出错。**累计次数是历史包袱，不是当前状态。**

改成只看「最近一次采集是否失败」：最近成功过就不再标。
这样标记的含义从「曾经出过事」变成「**这个数现在是旧的**」——后者才真需要提醒。

配套三条：
1. 用**中性灰**不用红色 —— 红色会让人以为出了业务事故，其实只是数据可能没更新
2. 悬停才给原因和「去采集管理看详情」的指引，不占视觉空间
3. 失败原因明细在采集日志里已经带商品名和原因（`fails` 字段），不用在主表格重复

代码：`store.collectHealth(db, productId)` → `lastFailed` / `lastFailReason` / `lastFailTs`；
前端 `staleMark()`。三处同步（`stats()` / `groupByShop()` / `groupCompare()`）。

## 8. 踩坑记录
| 坑 | 表现 | 解法 |
|---|---|---|
| 裸跑 `node server.js` | MODULE_NOT_FOUND: playwright | 带 `NODE_PATH` 和 `PLAYWRIGHT_BROWSERS_PATH`（见 6.2） |
| 跑全量测试前没重启服务 | MD5 校验误报「真实数据被污染」 | 先重启服务再跑 |
| 新增字段只加到 `stats()` | 表格里显示不出来 | `stats()` / `groupByShop()` / `groupCompare()` 三处同步 |
| 老 `test_today` 用例语义过期 | 「数字回退如实给负数」期望 −5，新规则下是 0 | 拆成「日切」（0 + todayCut 5）与「盘中」（−2）两种 |
| 测试用 `sched.nowHM()` 当槽位 | 加了可信时段后，凌晨跑测试会大面积变红 | 注入固定时刻 `AT = new Date(2026, 9, 21, 12, 0)` |
| UI 测试用 `nth(i)` 定位行 | 商品行按店铺分组 + 增量排序，行序不稳定 | 用 `.filter({ hasText: '关键词' })` 定位 |
| headless Chrome 退出时清临时文件 | 被沙箱拦截，任务标红但断言全过 | 已知噪音，看「结果: N 通过, 0 失败」即可，别看退出码 |
| UI 测试报 404 JS 错误 | 浏览器自动请求 `/favicon.ico` | 页面加 `<link rel="icon" href="data:,">`，从根上消掉，别在每个测试里各自过滤 |
| 关掉弹窗后内容留在 DOM 里 | 「页面上有没有日志区」这类判断失真 | `closeModal()` 里一并清空 `#mbox` |
| 店铺层「先加累计再相减」 | 新增商品当天凭空多出它一辈子的销量（+1635） | `ChartKit.sumDeltas()`：逐品先算周期增量再相加 |
| MD5 校验把正常采集误报成污染 | 服务在跑，脚本执行期间它自己采了 8 条 | 结构比对：只允许追加，禁止丢失/改写 |
| bash 里 `$BK）` 少写花括号 | `set -u` 下报 `BK：unbound variable`（全角括号被当变量名一部分） | 一律写 `${BK}` |
| 加购文案被当成销量 | 「24小时内123人加购」解析成"已售 24"——凭空造销量 | `parseSold()` 先确认是销量文案（含「已售/销量/…」）才解析 |
| 表头与行的列含义对不上 | 商品行第 6 格是「件/时」，表头写的是「价格」；窄屏一换行就读串行 | 表头/店铺行/商品行统一成 9 列，「件/时」挪进「最近增量」的悬停说明 |
| 手机端数字串列 | `td.num` 用 inline-block + margin 横排，数值长短不一就挤到别人的标签上 | 窄屏 `tr` 改 `display:grid`，标签 `::before` 改 `display:block` 放数值上方 |
| SVG 固定 680 宽 + `svg{width:100%}` | 窄屏把整张图等比缩小（680→344），10.5px 的标签实际只剩 5px，两张图都"压扁" | viewBox 按容器实际像素宽出图（1:1），窄屏另给高度 260；resize 时重画 |
| 窄屏横轴标签间距写死 44px | 344px 宽的画布放不下，标签互相挤掉 | `pickTicks` 接受 `minGap`，窄屏按可用宽度按比例收窄到 30px 起 |
| `nohup` 起的服务被沙箱回收 | 启动时 200，几分钟后 502，测试里报 `ERR_CONNECTION_REFUSED` | 用受管后台任务（`run_in_background`）起服务；`run_tests.sh` 先探测 7788 |
| 「无法运行」提示语指向错误方向 | 提示写"可能需要临时端口被占用"，实际是服务没起 | 按错误内容区分：连接被拒 → 说"服务没起"；其他 → 说"脚本异常退出" |
| 用**窗口内累计**次数表达采集健康度 | 07:31 后零失败，表里还挂「失败1」（都是 00:00 旧制度采的），像还在出错 | 只看「最近一次是否失败」；累计次数放采集日志 |
| 修接口字段时改了 store/server 却没重启服务 | 界面上新字段不生效，容易误判成代码写错了 | 改完 store.js / server.js 必须重启 7788；重启后核对 `/api/state` 里新字段在不在 |
| 浏览器通道只在接口失败时才走 | 接口成功但没带加购数时，页面上的加购永远抓不到 | 补一条：接口没拿到加购数时也走浏览器（须有登录态，否则白跑） |
| 商品页 innerText 长度 0 就以为没数据 | 风控挡了，页面还没渲染完 | 等 5~6 秒或用 `networkidle`；`domcontentloaded` + 短等待会拿到空串 |
| 搜索 JSON 里的关键词命中「心愿单」 | 那是顶部菜单的功能入口名，不是加购数据 → 假阳性 | 逐个打印全部中文叶子人工过一遍，别只看关键词命中数 |

## 9. 待观察

- **恢复窗口样本太少**：只有 3 个样本（15 分钟 / 30 分钟 / 8 小时），且只观察了 1 天。

  「今日增量」在跨天时确实稳定。
