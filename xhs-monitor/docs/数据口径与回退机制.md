# 数据口径与回退机制

这份文档记录「已售数字为什么会掉下去」「我们怎么判」「代码在哪」。
调研与落地时间：2026-10-20 ~ 2026-10-21。

**为什么单独写一份**：这件事上我们错过一次（把"延迟数据"当成了"剔除退款"），
而且错得很有说服力——数字确实掉了，掉完确实又涨回来了，只是涨回来的方式
暴露了真相。下次再遇到类似现象，先看这份文档的「证据链」部分，
别急着下结论。

---

## 0. 一分钟速查

| 问题 | 结论 |
|---|---|
| 数字掉下去了，怎么办？ | 分两种：涨得回来的 = 延迟数据，剔除；涨不回来的 = 真回调，如实显示负数 |
| 什么时候采集？ | 只在 **07:30–23:50**，凌晨不采 |
| 今日增量怎么算？ | 最新可信值 − 基线，基线 = **「昨日最后」与「今早首采」取低者** |
| 今日增量和图表数字对不上？ | 正常。**今日增量 = 图上今天的值 + todayCut** |
| 想改采集时间 | 页面右上角 ⏰；窗口外的时间点会标红且不会执行 |

## 1. 现象：凌晨的「已售」会掉下去

### 1.1 原始证据（2026-10-21，本地时间，来源 `data/snapshots.json`）

```
电容笔 pmvgmzka6
  10/20 23:40 = 1857  → 10/21 00:15 = 1860 → 00:30 = 1861 → 08:18 = 1868 → 10:04 = 1872
  （这条当天没掉，是前一版事故里的样本，见 1.3）

猫猫 pmvgpc6x5
  10/20 23:40 = 1661  → 10/21 00:15 = 1647 ↓  → 00:30 = 1662 ↑  → 08:18 = 1665 → 10:04 = 1667

森之物 pmvgrzoov
  10/20 23:40 =  556  → 10/21 00:15 =  550 ↓  → 00:30 = 550 → 08:18 =  557 ↑  → 10:04 = 557

眼罩 pmvgqwp4z
  全程 54000 不变（原文「已售5.4万+」，见第 2 节）
```

两条掉下去、之后又涨回来，**还涨过了掉之前的高点**（1662 > 1661，557 > 556）。

### 1.2 第一版结论：错的

> 「0 点数字下降 = 平台在日切时剔除退款/取消单」

这个结论看着很合理，也符合业务常识。当时的实现是：给 0 点那条特殊待遇，
把它当今日基线，这样日切修正就不会算进当天销量。

**它错在哪**：如果真是剔除退款，数字掉下去之后**不可能自己涨回来**。
退款只会让累计件数减少，不会还回来。而实测里它涨回来了，还超过了掉之前的高点。

更细的反证：电容笔那次 15 分钟涨了 82 件（1778 → 1860），发生在午夜。
这个速率在凌晨不合常理。

### 1.3 正确结论：凌晨读到的是旧快照

**掉下去 → 之后涨回并超过掉之前的高点 ⇒ 那条低读数是延迟数据，不是真实销量。**

判定只需要一个事实：**之后有没有涨回到那个高点**。不需要设阈值
（设阈值就又回到"猜"了，而且我们在这上面已经错过一次）。

补充证据：正常时段用探针连打 8 次（间隔 9 秒），读数完全一致 —— 不抖。
问题只出现在日切窗口。

## 2. 另一个独立问题：高销量商品是取整显示

`priceH5.itemAnalysisDataText` 的分辨率：

| 已售量级 | 原文 | 分辨率 |
|---|---|---|
| < 1 万 | `已售1868` | 精确，1 件 |
| ≥ 1 万 | `已售5.4万+` | **1000 件一档** |

所以「眼罩」那条平线不是没卖，是档位太粗看不出来。

- 采集侧：`api_collect.js` 的 `soldResolution(raw)` 解析出 `{approx, step}`
- 历史数据（没有这两个字段的老快照）：`store.js` 的 `coarseInfo(snap)` 从 `note` 反推
- 界面：累计值显示 `≈54,000*`，悬停说明"平台按 1,000 件一档"

**这类商品的今日增量可能是 0，不代表没卖。**

## 3. 规则总览：两道防线 + 一个基线

```
原始快照序列
    │
    ├─ 第一道：soldSeries()          ← 剔除「涨回来了」的延迟数据
    │
    ▼
可信序列（单调不减，除非真回调）
    │
    ├─ 第二道：TRUST_WINDOW          ← 源头不采，避免"没机会翻案"的脏数据
    │          （07:30–23:50）
    │
    ▼
今日基线 todayBaseline()             ← 「昨日最后」与「今早首采」取低者
    │
    ▼
今日增量 todayDelta()
```

### 3.1 第一道防线：过期读数剔除

**位置**：`store.js` → `soldSeries(db, productId)`

```
遍历按时间排序的成功快照，维护当前高点：
  当前值 < 高点 ？
    ├─ 之后有一条 ≥ 高点  →  剔除（延迟数据）
    └─ 之后再没回到高点   →  保留（真回调，如实显示负增量）
```

三条性质：

- **只用事后可知的事实**，不设阈值
- **最后一条如果是掉下来的，暂时判不了，先保留** —— 它本来就是最新事实
- 涨回去但**没超过**高点 → 保守保留（不敢断言）

被剔除的记录在历史弹窗里标「过期读数·已剔除」，**不算采集失败**。

### 3.2 第二道防线：可信时段

**位置**：`scheduler.js` → `TRUST_WINDOW = { start: '07:30', end: '23:50' }`

**为什么有了第一道还要第二道**：`soldSeries` 是事后补救，前提是后面得有一条
涨回来的记录。若凌晨那条恰好是当天最后一条（服务停了、下次采集失败），
它就**再也没机会翻案**，会被永久当成真实退款留在数据里。

与其事后救，不如源头别采。

**代价**：看不到 00:00–07:30 的分时走势。但这几个小时的销量不会丢，
整段归到当天（按日统计本来就该这样算）。

生效范围（三处，缺一不可）：

| 位置 | 行为 |
|---|---|
| `shouldRunNow()` | 窗口外的槽位一律不执行 |
| `nextRun()` | 过滤窗口外槽位，否则会显示一个永不执行的「下次执行」 |
| `server.js` 启动逻辑 | 「启动即采集」同样受限 —— 凌晨重启服务不会抢跑一次 |

界面侧：设置弹窗里窗口外的时间点**标红 + 文字警告**，避免"设了却不知道不执行"。

### 3.3 今日基线：取低者

**位置**：`store.js` → `todayBaseline(db, productId, refTs)`

```
候选 A = 昨日最后一次可信读数
候选 B = 今天第一次可信读数

基线 = min(A, B)
  - 通常 B > A（夜里一直在卖） → 用 A，夜间销量算今天
  - B < A → 用 B。那笔下修发生在昨天和今天之间，不该把今天的数字压成负数
```

#### 易错点 1：阈值拿「昨日最后」比，不是「昨日最大」

昨天盘中出过真退款时，两者不等：

```
昨天 12:00 = 1000
昨天 18:00 =  990   ← 真退款，之后再没回到 1000
昨天 23:49 =  990   ← 昨日最后
今早 07:31 =  995   ← 比昨夜高 5 件（货真价实的夜间销量），但比昨天最高点低 5 件
今天 12:00 =  998
```

- 拿「最后 990」比：995 > 990 → 基线 990 → 今日 **+8** ✅
- 拿「最大 1000」比：995 < 1000 → 误判"今早掉了" → 基线 995 → 今日 +3，白丢 5 件

**用例**：`test_rollback.js` 的 C 组专门钉住这点。

#### 易错点 2：这条规则只在「全天没涨回昨夜高点」时才会触发

```
昨夜 23:49 = 1000
今早 07:31 =  993   ← 更低
今天 12:00 = 1030   ← 但涨回来了，还超过了 1000
```

这种情况下 `soldSeries` **早就**把 993 当延迟数据剔除了，轮不到基线规则。
序列变成 `[1000, 1030]`，基线仍是 1000，今日 +30，吸收量为 0。

**两道防线各管一段**：`soldSeries` 先筛假回退，基线规则只处理剩下的真下修。

**用例**：`test_rollback.js` 的 B2 组钉住这点。万一哪天 `soldSeries` 被改坏
（比如把这条低读数留下了），那条用例会立刻变红。

### 3.4 不静默吞账：`todayCut`

今早首采更低时改用 B 当基线，会**吸收掉一笔下修**：

```
昨夜 1000 → 今早 993 → 中午 998
今日增量 = 998 − 993 = +5
但累计其实比昨夜低 2 件 —— 看着在涨，实际在跌
```

所以吸收量记在 `todayCut`，沿三条链路带到界面：

- `store.stats()` → `todayCut` / `todayBase`
- `store.groupByShop()` / `store.groupCompare()` → 同上
- `server.js` 的 `/api/state` → 同上

界面：数字后紧跟 `↧7`，鼠标悬停显示
「今早首采比昨夜低 7 件，已改用它作今日基线，这笔下修未计入今日增量」。

## 4. 与图表的关系（两者会差一个数，这是有意的）

| 口径 | 算法 | 上例结果 |
|---|---|---|
| 按日销量图 | 本期最后 − 上期最后 | 945 − 1000 = **−55** |
| 今日增量 | 最新 − min(昨日最后, 今早首采) | 945 − 940 = **+5** |

**恒等关系：今日增量 = 图上今天的值 + todayCut**（−55 + 60 = 5）。

图表现的是"累计口径的变化"，今日增量表现的是"今天的经营结果"。
两个都要，不要试图统一——统一就意味着有一边在说谎。

## 5. 代码位置速查

| 关注点 | 文件 | 函数 / 常量 |
|---|---|---|
| 过期读数剔除 | `store.js` | `soldSeries()` |
| 可信时段 | `scheduler.js` | `TRUST_WINDOW`、`timeInWindow()`、`inTrustWindow()` |
| 到点判定 | `scheduler.js` | `shouldRunNow(cfg, now)`、`nextRun(cfg)` |
| 今日基线 | `store.js` | `todayBaseline()` |
| 今日增量 | `store.js` | `todayDelta()` |
| 取整识别（采集） | `api_collect.js` | `soldResolution()` |
| 取整识别（历史） | `store.js` | `coarseInfo()` |
| 回退分级 | `store.js` | `classifyDrop()` |

| 界面渲染 | `web/index.html` | `todayCell()`、`cumCell()`、`openSched()` |

**改动这三处时，记得同步**：`stats()` / `groupByShop()` / `groupCompare()`
都各自组装商品对象，新增字段要三处都加，否则界面某几个视图会拿不到。
（这次 `todayCut` 就漏了 `groupByShop()`，表格里显示不出来，被 UI 测试抓到了。）

## 6. 操作手册

### 6.1 改采集时间

页面右上角 ⏰。当前设置：

```
07:31   10:00   12:00   15:00   18:00   21:00   23:49
```

也可以直接改 `data/schedule.json`（服务每 20 秒重读一次，不用重启）：

```json
{
  "enabled": true,
  "times": ["07:31", "10:00", "12:00", "15:00", "18:00", "21:00", "23:49"],
  "runOnStart": true
}
```

> **末采 23:49 为什么重要**：它同时是明天的基线起点。原来末采是 21:00，
> 意味着**昨天 21:00–24:00 那 3 小时的销量被算进了今天**。挪到 23:49 后，
> 归属误差从 3 小时缩到 11 分钟。这个收益跟凌晨脏数据无关，是独立的口径修正。

### 6.2 重启服务

**必须带两个环境变量**，否则 `collect.js` 引不到 playwright，直接 MODULE_NOT_FOUND：

```bash
cd xhs-monitor
NODE_PATH=~/.workbuddy/binaries/node/workspace/node_modules \
PLAYWRIGHT_BROWSERS_PATH=~/.workbuddy/binaries/node/workspace/browsers \
PORT=7788 node server.js
```

跟 `启动监控.command` 里的写法保持一致。

启动后日志会打印可信时段和下次执行时间，用来确认配置生效：

```
  采集时间: 07:31、10:00、12:00、15:00、18:00、21:00、23:49
  可信时段: 07:30–23:50（窗口外不采集，凌晨会读到旧快照）
  下次执行: 2026/10/21 12:00:00
```

### 6.3 改配置 / 改逻辑后怎么验证

```bash
cd xhs-monitor
bash run_tests.sh          # 全部（约 2.5 分钟）
bash run_tests.sh core     # 只要不需要浏览器的那批（约 20 秒）
```

`run_tests.sh` 会先把 `data/snapshots.json`、`data/schedule.json` 备份到
`backups/<时间戳>/`，跑完比对 MD5，一旦被测试改动就打印还原命令。

**跑全量前先重启服务**。旧进程没有窗口守卫，可能按旧时间表在测试期间采集，
改动 `snapshots.json` → MD5 校验误报「被污染」。

### 6.4 核对当前数据

```bash
curl -s http://127.0.0.1:7788/api/state | python3 -c "
import json,sys
s = json.load(sys.stdin)
print('今日增量合计:', s['totals']['today'])
for p in s['products']:
    cut = f\"  ↧{p['todayCut']}\" if p.get('todayCut') else ''
    print(f\"{(p['name'] or '')[:20]:22} 累计 {p['cumulative']:>6}  今日 {p['todayDelta']:>4}{cut}  基点 {p.get('todayBase')}\")
"
```

## 8. 踩坑记录

| 坑 | 表现 | 解法 |
|---|---|---|
| 裸跑 `node server.js` | MODULE_NOT_FOUND: playwright | 带 `NODE_PATH` 和 `PLAYWRIGHT_BROWSERS_PATH`（见 6.2） |
| 跑全量测试前没重启服务 | MD5 校验误报「真实数据被污染」 | 先重启服务再跑 |
| 新增字段只加到 `stats()` | 表格里显示不出来 | `stats()` / `groupByShop()` / `groupCompare()` 三处同步 |
| 老 `test_today` 用例语义过期 | 「数字回退如实给负数」期望 −5，新规则下是 0 | 拆成「日切」（0 + todayCut 5）与「盘中」（−2）两种 |
| 测试用 `sched.nowHM()` 当槽位 | 加了可信时段后，凌晨跑测试会大面积变红 | 注入固定时刻 `AT = new Date(2026, 9, 21, 12, 0)` |
| UI 测试用 `nth(i)` 定位行 | 商品行按店铺分组 + 增量排序，行序不稳定 | 用 `.filter({ hasText: '关键词' })` 定位 |
| headless Chrome 退出时清临时文件 | 被沙箱拦截，任务标红但断言全过 | 已知噪音，看「结果: N 通过, 0 失败」即可，别看退出码 |

## 9. 待观察

- **恢复窗口样本太少**：只有 3 个样本（15 分钟 / 30 分钟 / 8 小时），且只观察了 1 天。
  可选实验：00:00–00:40 每 2 分钟探针一次，把恢复曲线摸清。
  现在既然不采了，这个实验的价值主要在于"知道窗口能收窄到几点"。
- **`soldSeries` 的边界情形**：真实退款 + 后续新销量把数字推回高点之上时，
  两者在数据上完全一样（都是"掉下去又涨过前高"），当前一律判为延迟数据。
  真要区分只能靠速率，但那又要设阈值。目前接受这个近似。
- **23:49 末采的实际效果**：还需要跑满一个完整的日切周期才能确认
  「今日增量」在跨天时确实稳定。
